# NyxilumDb

Легка embedded key-value база даних на C#/.NET з Write-Ahead Log (WAL)
для довговічності — натхненна внутрішнім устроєм Redis/SQLite. Один з
трьох "проєктів з нуля", запропонованих AI-оглядом GitHub-профілю
(інші два: [nyxilum-mcp](https://github.com/Faneraiy14/NyxilumMcp) — уже
готовий; власний HTTP-сервер — поки в беклозі).

## Чому не просто `Dictionary` з `File.WriteAllText`

Тому що тоді збій процесу посеред запису означає втрату/пошкодження
даних. WAL-модель: кожен `Set`/`Delete` спершу дописується (і за
потреби — `fsync`) у лог, і лише ПОТІМ застосовується до пам'яті. При
перевідкритті лог відтворюється — навіть якщо останній запис обірвався
рівно посеред запису на диск, усе, що ДО обриву, лишається дійсним.

## Швидкий старт

```csharp
using var db = NyxilumDb.NyxilumDb.Open("./mydata");

db.Set("greeting", Encoding.UTF8.GetBytes("Привіт!"));
var value = db.Get("greeting"); // byte[]?

foreach (var (key, val) in db.Scan("user:"))
    Console.WriteLine($"{key} = {Encoding.UTF8.GetString(val)}");

db.Delete("greeting");
```

Повний приклад — [samples/NyxilumDb.Demo](samples/NyxilumDb.Demo/Program.cs).

## Модель довговічності

- `FsyncMode.Always` (типово) — `FlushFileBuffers` після КОЖНОГО запису.
  Єдиний режим, де "виклик повернувся" реально означає "переживе
  зникнення живлення". Повільніше (реальний диск-I/O на кожен запис).
- `FsyncMode.OsBuffered` — покладається на буфер ОС. Переживає падіння
  процесу (crash), але не втрату живлення протягом кількох секунд до
  фактичного запису на диск. Значно швидше — придатний, коли важлива
  пропускна здатність, а не гарантія на рівні "вимкнули живлення".

## Компакція (checkpoint)

WAL, що росте вічно, — не варіант для чогось довше "разової демки".
Після перевищення `CheckpointThresholdBytes` (типово 4 МБ) поточний
стан пам'яті пишеться у знімок (`.snap`), і WAL обрізається до
заголовка. Знімок без валідного футера (перевіряється контрольною
сумою) повністю ігнорується при відкритті — тому напівзаписаний
знімок після збою посеред компакції нешкідливий: `Set`/`Delete`
ідемпотентні (останній запис за ключем перемагає), тож повторне
застосування вже застосованих записів з WAL після невдалої компакції
не змінює результат.

## Модель конкурентності

Один `ReaderWriterLockSlim` на все сховище: один писач одночасно,
довільна кількість читачів паралельно. Запис у WAL відбувається
ВСЕРЕДИНІ write-замка — порядок запису в лог завжди збігається з
порядком застосування до пам'яті.

## Обмеження v1

- Весь набір даних мусить влізти в пам'ять (`SortedDictionary`, не
  дисковий B-Tree) — свідомий вибір для першої версії: дисковий індекс
  нічого не додав би, поки й так усе в RAM.
- `Scan`/`Range` — O(n) прохід, не оптимізований дисковий діапазонний
  пошук.
- Один процес на базу (WAL-файл ексклюзивний для writer'а).

## Тести

```bash
dotnet run --project tests/NyxilumDb.Tests
```

24 перевірки без фреймворку (як `run_all.sh` у NyxilumLang): перезапуск
процесу з даними, що переживають Close/reopen; обірваний/пошкоджений
WAL (обрізання на 1/4/9 байт, зіпсований байт усередині запису, сміття
в кінці) — переконатись, що replay коректно відкидає ТІЛЬКИ хвіст;
реальний crash дочірнього процесу (`Process.Kill()`, не керований
виняток) з перевіркою, що всі підтверджені записи вижили; компакція
(знімок створюється, WAL стискається, дані цілі після reopen);
конкурентні читачі/писачі (4 потоки запису + читач, без деадлоку й
пошкодження); fuzz-тест проти `Dictionary`-оракула з періодичним
reopen.
